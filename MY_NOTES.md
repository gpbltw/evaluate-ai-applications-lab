## Что понял

### 1. Rubric — не «хорошо/плохо», а шкала

Оценка должна иметь явные уровни (1–7 для полноты, 1–3 для прямоты),
нормализацию в 0..1 для порога и явный threshold pass/fail.
Без этого два ревьюера поставят разные оценки одному ответу.

### 2. Датасет должен быть сбалансирован

Если в наборе только «правильные» ответы — pass rate 100% ни о чём
не говорит. Нужно 20–30% граничных или намеренно плохих кейсов,
чтобы увидеть чувствительность judge'а.

### 3. Threshold — инженерное решение, не «правильный ответ»

Зависит от цены ошибки:
- безопасность / деньги / юридическое — 100% (или human-in-the-loop);
- важные процедуры — 95%;
- информационные — 85%;
- стилистика — 70%.

Единый порог для всех категорий — плохая практика.

### 4. False positives опаснее false negatives

Пропустить плохой ответ хуже, чем завалить хороший. В критичных
категориях это может привести к ущербу (деньги, безопасность).

### 5. Разделение детерминированных и семантических проверок

- Формат, ID, точные значения → детерминированные (regex, equals);
- Полнота, стиль, полезность → модельные rubric;
- Смешивать нельзя — либо точность, либо покрытие теряются.

## Вывод

Judge справляется с **явными** проблемами (не ответил на вопрос),
но ошибается на **граничных** случаях («правильно, но не идеально»).

Для production нужно:
- либо более крупный judge (`gpt-oss-120b`);
- либо калибровка thresholds по категориям;
- либо human review для критичных кейсов.
